import { browserhivePin } from "../../lib/extract";

capture-ledger is pinned to a **specific BrowserHive version**, not to `main`. The
current pin is **{browserhivePin()}**.

That comes from the `.upstream/browserhive` submodule — read at build time with
`git describe --tags`, so this page cannot go stale. The submodule carries BrowserHive,
the `chromium-server-docker` BrowserHive was tested against, the signing services
(`wacz-signer`, `timestamp-authority`), and the OpenAPI document
(`generated/openapi.json`) the manifest is checked against. It is not the only upstream
pin: the object store's startup config comes from `.upstream/seaweedfs`, the WACZ viewers
from `.upstream/replayweb-server` (unmodified ReplayWeb.page) and `.upstream/capture-player`
(the modified Web Capture viewer), the capture fixtures from `.upstream/capture-fixtures` and the
scripts from `.upstream/capture-scripts`. Each is pinned to its own tag and none moves
with this one (the head of `docker-compose.yml` says why the ones the stack builds from are separate).

:::note[It used to be four places]
The version was once written out in `package.json`, setup.sh (since removed)
and two compose files, with a check that they agreed. The submodule replaced all four, so there
is nothing left to keep in sync.
:::

## Procedure

```sh
# 1. Move the submodule to the new tag.
git -C .upstream/browserhive fetch --tags
git -C .upstream/browserhive checkout <new-tag>
git -C .upstream/browserhive submodule update --init --recursive
git add .upstream/browserhive

# 2. Re-vendor the contract and regenerate the types (a local copy — no network).
pnpm run openapi:generate
pnpm run openapi:check     # must exit 0 once committed

# 3. Rebuild the dev stack from the new submodule. Name the fixtures' service:
#    without it, stack:up recreates every container in the stack.
pnpm run dev:down
pnpm run dev:up
pnpm run stack:up --profile capture-fixtures capture-fixtures

# 4. Prove it end to end.
pnpm run check
(cd ../capture-scheduler && pnpm run smoke)
```

Chromium follows automatically: it is a submodule of the submodule, so you get
the version BrowserHive itself was tested against. capture-ledger used to track it
independently at `main`, and that is exactly how a stack break arrived — upstream
moved its development Dockerfile into `attic/` and every build stopped working.

## Choosing a version

:::danger[Check that the version can build]
The stack builds BrowserHive's `Dockerfile.prod` from the submodule, so a commit
whose Dockerfile is broken takes the whole stack down with it. This has already
happened twice, both times with the same file. Between `8a66b72` and `b772480` a
COPY source was missing from BrowserHive's whitelist dockerignore; from BrowserHive
`8c899dd` until `a218e94` the COPY kept naming `tsconfig.behaviors.json` after the
file itself was deleted. Everything in either range fails with
`"/tsconfig.behaviors.json": not found`. **v11.0.0 builds**; anything pinned inside
the second range does not.

Verify before committing the submodule bump:

```sh
# -f resolves from where you stand, not from the context, so it needs the
# path including the context. Plain `-f Dockerfile.prod` fails with
# "dockerfile does not exist".
container build -f .upstream/browserhive/Dockerfile.prod -t bh-probe .upstream/browserhive
```

:::

## What changes on the capture-ledger side

An additive API change — new optional request fields — needs nothing beyond
step 2: the regenerated types still compile and the tests pass untouched. That
was the case for 1.6.0. Upstream runs `smithy diff` against the previous release
on every change, so a bump that only adds members cannot have renamed or retyped
an existing one out from under the copy.

Infrastructure changes are the ones that bite, because they do not show up in
the OpenAPI diff at all. Two examples from the 1.5.2 → 1.6.0 move:

- BrowserHive's SeaweedFS entrypoint started creating the bucket itself, which
  made capture-ledger's own one-shot init container redundant (and its `depends_on`
  guarantee obsolete — `WAIT_FOR_S3` replaced it).
- The upstream Chromium image moved its development Dockerfile to `attic/`.

After bumping, read the upstream release notes for anything that touches
`etc/seaweedfs/*`, the entrypoint, or the compose contract.

### What the manifest check accepts

The level handler, reconcile, the log route and the trace route read every `.result.json` through
`readManifest` (`src/archive/manifest.ts`), which checks it with Ajv against the copy of
`CaptureResultReport`. What a bump changes there:

- **Members the copy does not know pass.** A manifest from a newer BrowserHive is still
  read, so a BrowserHive release does not stop the ledger before the copy is bumped.
  An enum value the copy does not know does not pass: until the copy is bumped, the level
  handler and reconcile skip that manifest, and the log and trace routes answer
  `manifest-invalid`.
- **A member the contract gives a default is filled in when missing** (`useDefaults`), so
  a member that later became required with an `@default` does not fail old manifests. One
  that became required _without_ a default, or an enum value that was removed, does —
  before bumping, compare `required` and `enum` between the old and the new `openapi.json`.
- **An optional member stays absent.** `log` (v24.0.0) has no default, so a manifest
  written before it reads without `log` rather than with an empty one — which is how the
  log route can say `no-log` instead of showing an empty log.
- **A `format` in the contract stops the API.** Ajv knows neither `date-time` nor `double`
  (there is no ajv-formats), and compiling throws as soon as `src/archive/manifest.ts` is
  imported: the API does not start, and every test that reads a manifest fails. Only the
  schemas reachable from `CaptureResultReport` are compiled, so check those for a new
  `format` before bumping.
