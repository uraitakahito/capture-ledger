---
title: Upgrading BrowserHive
description: How to move capture-ledger to a newer BrowserHive version, and what can go wrong.
---

import { browserhivePin } from "../../lib/extract";

capture-ledger is pinned to a **specific BrowserHive version**, not to `main`. The
current pin is **{browserhivePin()}**.

That comes from the `.upstream/browserhive` submodule — read at build time with
`git describe --tags`, so this page cannot go stale. The submodule is the _only_
upstream pin: it carries BrowserHive, the `chromium-server-docker` BrowserHive
was tested against, the SeaweedFS config the stack mounts, and the `.proto`
the client is generated from.

:::note[It used to be four places]
The version was once written out in `package.json`, setup.sh (since removed)
and two compose files, with a check that they agreed. The submodule replaced all four, so there
is nothing left to keep in sync.
:::

## Procedure

```sh
# 1. Move the submodule to the new tag.
git -C .upstream/browserhive fetch --tags
git -C .upstream/browserhive checkout <new-tag>
git -C .upstream/browserhive submodule update --init --recursive
git add .upstream/browserhive

# 2. Re-vendor the contract and regenerate the stubs (a local copy — no network).
pnpm run proto:sync
pnpm run proto:generate
pnpm run proto:check       # must exit 0 once committed

# 3. Rebuild from a clean state. Old volumes hold the previous bucket and
#    database, which hides ordering bugs introduced by the upgrade.
pnpm run stack:down
pnpm run stack:up

# 4. Prove it end to end.
pnpm run check
./scripts/prod-smoke.sh
```

Chromium follows automatically: it is a submodule of the submodule, so you get
the version BrowserHive itself was tested against. capture-ledger used to track it
independently at `main`, and that is exactly how a stack break arrived — upstream
moved its development Dockerfile into `attic/` and every build stopped working.

## Choosing a version

:::danger[Check that the version can build]
The stack builds BrowserHive's `Dockerfile.prod` from the submodule, so a commit
whose Dockerfile is broken takes the whole stack down with it. This has already
happened once: between `8a66b72` and `b772480` a COPY source was missing from
BrowserHive's whitelist dockerignore, and everything in that range fails with
`"/tsconfig.behaviors.json": not found`.

Verify before committing the submodule bump:

```sh
# -f resolves from where you stand, not from the context, so it needs the
# path including the context. Plain `-f Dockerfile.prod` fails with
# "dockerfile does not exist".
container build -f .upstream/browserhive/Dockerfile.prod -t bh-probe .upstream/browserhive
```

:::

## What changes on the capture-ledger side

An additive API change — new optional request fields — needs nothing beyond
step 2: the regenerated types still compile and the tests pass untouched. That
was the case for 1.6.0. Upstream runs `buf breaking` on every change, so a bump
that only adds fields cannot have moved a field number out from under the
generated code.

Infrastructure changes are the ones that bite, because they do not show up in
the `.proto` diff at all. Two examples from the 1.5.2 → 1.6.0 move:

- BrowserHive's SeaweedFS entrypoint started creating the bucket itself, which
  made capture-ledger's own one-shot init container redundant (and its `depends_on`
  guarantee obsolete — `WAIT_FOR_S3` replaced it).
- The upstream Chromium image moved its development Dockerfile to `attic/`.

After bumping, read the upstream release notes for anything that touches
`etc/seaweedfs/*`, the entrypoint, or the compose contract.
