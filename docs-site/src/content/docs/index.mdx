## What capture-ledger is

capture-ledger answers one question: **which URLs get captured**. A caller asks for a
crawl; capture-ledger works out the seeds — an explicit list, or the enabled rows of a
Postgres `capture_targets` table — decides what is in scope, and hands one level
at a time to a Windmill flow that does the submitting.

## What is not capture-ledger's responsibility

Driving a browser, taking screenshots, building a WACZ, writing to S3 — every
one of those is **BrowserHive's responsibility**. BrowserHive's docs are not
published on the web — build them from the BrowserHive checkout with
`pnpm run docs:local`.

**Submitting is not capture-ledger's either, any more.** The Windmill flow in
[capture-scheduler](https://github.com/uraitakahito/capture-scheduler) holds the gRPC channel, and
capture-ledger has no BrowserHive address in its configuration at all. Each level the
flow reports comes back with a `taskId` per page, and capture-ledger registers what
produced an archive in the [archive ledger](/capture-ledger/archive-ledger/). Anything
the level handler failed to admit is picked up later by `pnpm run fga:reconcile`,
which reads the manifest keys those reports recorded.
