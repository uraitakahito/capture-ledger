**定期実行の時計は capture-ledger の中に在ります。** API のプロセスが 30 秒ごとに予定の表（`crawl_schedules`）を見て、
期限の来た予定からクロールを 1 本始めます。Windmill は頼まれた段を撮るだけで、いつ撮るかを知りません。

画面は capture-workbench のタブ「定期実行」です。
ここでは capture-ledger の側の決まりを書きます。

## 周回の 1 回

1. 走行中のクロールが在れば何もしません（全体で 1 本だけ走る決まりです）。
2. 「いま撮る」の頼みが在る予定を先に、次に期限の古い予定を 1 つ選びます。
3. 期限で始める予定は、**静かな時間**を見ます。API の起動と直近のクロールの両方から
   `CAPTURE_LEDGER_SCHEDULE_QUIET_MINUTES`（既定 10 分）が過ぎるまで始めません。「いま撮る」は見ません。
4. 宣言されたシークレットが Windmill に在るかを訊きます。
5. 1 つのトランザクションで、クロールの行と起点のページを足し、次の回へ進めます。
6. commit の後で webhook を投げます。

| 起きたこと                                                | どうなるか                                                                              |
| --------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| 走行中の行とぶつかった                                    | rollback します。期限は動かず、順番待ちのまま残ります。「見送り」という結末はありません |
| シークレットが足りない・Windmill に訊けない・行を足せない | `failed` の行を足し、次の回へ進みます                                                   |
| webhook を投げられなかった                                | 行を `failed` で閉じます（手で始めたクロールと同じです）                                |
| capture-ledger が止まっていた                             | 戻ったときに 1 回だけ撮ります。過ぎた回の数は `crawls.schedule_missed` に残ります       |

走ったまま止まった行は、周回が勝手に閉じません。本当に走っている回を閉じないためです。その予定自身の直近の回が
1 時間以上 `running` のとき、状態が `stuck` になり、画面の「締める」か `POST /api/crawls/:id/failed` で閉じます。
手で始めたクロールが塞いでいるときは、予定は `blocked` で、期限から 1 時間たつと `overdue` になります
（[状態の語](#状態の語)）。

## 撮り方の固定

予定を作ったときに、`POST /api/crawls` と同じ確かめを通して解決した撮り方を `recipe` に残します。
スクリプトの本文の写しまで入るので、新しい版が出ても回の中身は変わりません。答えの `outdated` が
`true` になり、人が `repin` で固定し直します。シークレットだけは宣言を持ち、回ごとに Windmill へ訊き直します。

回の行には撮り方の digest（`crawls.recipe_sha256`・`035`）も入ります。中身はスクリプトの id・版・phase・sha256・
options、変数の値、User-Agent、宣言したシークレットの名前で、ページの中身を変えうる物だけです。起点・規則・
`maxDepth`・`maxPages`・間隔は入れません。前回からの変化は、同じ予定でこれが同じ回どうしだけを比べます
（変数を替えて固定し直した回は、前の回と比べません）。`035` より前の行は `pnpm run changes:backfill` が埋めます
（`--schedule <id>` でその予定の回だけ）。

## エンドポイント

どのエンドポイント（HTTP の method と path の組）も `maySubmit` で絞ります。一覧は 200 の空、それ以外は 404 で答えます。操作はすべて POST です
（capture-workbench の中継の書き込みは POST だけです）。

| エンドポイント                   | すること                                                                                                                                                                               |
| -------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /api/schedules`            | 本文は `{name, cron, request}`。`request` は `POST /api/crawls` と同じ形で、同じ理由で断ります。cron は 5 欄だけ受け、続く 20 回の間隔が下限より短ければ 400 です。同じ名前は 409 です |
| `GET /api/schedules`             | 消していない予定を、状態と直近の回つきで返します                                                                                                                                       |
| `GET /api/schedules/:id`         | 1 本。形は一覧の要素と同じです                                                                                                                                                         |
| `POST /api/schedules/:id/pause`  | 止めます。待っている「いま撮る」の頼みも消します。走っている回はそのままです                                                                                                           |
| `POST /api/schedules/:id/resume` | 再開します。次の期限は今から計算し直し、止めていた間は欠けに数えません。止めていない予定には何もしません                                                                               |
| `POST /api/schedules/:id/run`    | いま撮ります。202 を返し、周回が始めます。止めた予定でも撮れます                                                                                                                       |
| `POST /api/schedules/:id/repin`  | 頼みをいまの capture-ledger で解決し直します。スクリプトが消えていれば同じ理由で断ります                                                                                               |
| `POST /api/schedules/:id/delete` | 消します。行は残ります（クロールの行に名前を出すためです）                                                                                                                             |

`GET /api/crawls` と `GET /api/crawls/:id` は、`schedule`（`{id, name}` か `null`）・`scheduledFor`・
`scheduleMissed` も返します。

## 状態の語

`health` は上から順に見ます。文は capture-workbench が作り、capture-ledger は語だけを返します。

| `health`  | 条件                                                              |
| --------- | ----------------------------------------------------------------- |
| `paused`  | 止めている                                                        |
| `stuck`   | 直近の回が 1 時間以上 `running` のまま                            |
| `overdue` | 期限または「いま撮る」の頼みから 1 時間以上たっても始まっていない |
| `failing` | 直近の回の `state` が `failed`                                    |
| `blocked` | 期限は来たが、走行中か静かな時間の待ち                            |
| `ok`      | 上のどれでもない                                                  |

`stuck` を分けているのは、毎日の予定は次の期限が約 24 時間先だからです。期限だけで見ると、04:00 に止まった回が
翌朝の 05:00 まで何も言いません。

## 前回からの変化

予定の回が締まると、capture-ledger の周回（30 秒ごと・1 本ずつ）が、同じ予定で撮り方の digest が同じ 1 つ前の回と、
ページの URL で組にして文字を比べます（CAPTURE-167）。比べる行は after-behaviors の写し、無ければ文書の行です。
伏せたページは比べません。

1. **比べる（Claude なし）。** 文字の digest（`archive_pages.text_sha256`）が同じページは WACZ を開きません。
   違うページだけ前と今の WACZ を保管庫から読み直し、行の差分（前後 2 行の文脈つき）を `page_changes` に残します。
   差分は 2 本の WACZ から作り直せます。全部同じなら `unchanged` で、費用は掛かりません。
2. **要約する（Claude を 1 回）。** 違ったページの差分をまとめて Claude に読ませ、ページごとの重さ
   （`none`・`minor`・`content`）と 1 行、回の 1 行を派生の層（`derivations`・`kind = 'change'`）に残します。
   Claude が読むのは差分の行と前後 2 行だけで、ページの文字の全部・伏せた文書・シークレットの値は送りません。
   引用は差分の変わった行に照らし、在らない物に印を付けます。**要約は証拠ではありません**（正は 2 本の WACZ と差分）。

| 状態          | 意味                                                                                       |
| ------------- | ------------------------------------------------------------------------------------------ |
| `no_previous` | 同じ予定・同じ撮り方の前の回が無い                                                         |
| `unchanged`   | どのページも文字が同じ（WACZ も Claude も呼ばない）                                        |
| `diffed`      | 差分を残した。鍵（`CAPTURE_LEDGER_ANTHROPIC_API_KEY`）が無ければここで終わり               |
| `summarized`  | 要約を残した                                                                               |
| `budget_wait` | 組織の月の上限（直す係と共有）に届いた。1 時間ごとに見直し、月が替わるか上限を上げると進む |
| `failed`      | Claude が 3 回答えなかった（1・5・30 分を空けた）か、断った                                |

拾うのは締まって 48 時間以内の回だけです（`035` より前の回は、`pnpm run changes:backfill` で digest を埋めると拾えます）。予定の答え（`GET /api/schedules`）の `recentRuns[].change` に、状態・比べた数・
違った数・重さ・1 行の写しが載ります。中身は `GET /api/changes?before=`（回のまとめの一覧）と
`GET /api/crawls/:id/changes`（ページごとの差分・要約・前と今の WACZ）で読み、どちらも `can_submit` で通し、
前と今の WACZ を `can_view` で見てよいページだけを返します。

## 設定

| 環境変数                                       | 既定 | 効果                                                                            |
| ---------------------------------------------- | ---- | ------------------------------------------------------------------------------- |
| `CAPTURE_LEDGER_SCHEDULE_QUIET_MINUTES`        | `10` | 静かな時間。`dev:up` がトークンを発行し直す前と、e2e の間に割り込まないためです |
| `CAPTURE_LEDGER_SCHEDULE_MIN_INTERVAL_MINUTES` | `60` | 周期の下限                                                                      |

クロールのエンドポイント（webhook の 2 行）が無い配備では、予定のエンドポイントも周回もありません。
