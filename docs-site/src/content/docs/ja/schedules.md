title: 定期実行
description: 予定の表と、台帳の中で 30 秒ごとに回る時計。口と状態の語。
---

**定期実行の時計は台帳の中に在ります。** API のプロセスが 30 秒ごとに予定の表（`crawl_schedules`）を見て、
期限の来た予定からクロールを 1 本始めます。Windmill は頼まれた段を撮るだけで、いつ撮るかを知りません。

画面は capture-workbench のタブ「定期実行」です。
ここでは台帳の側の決まりを書きます。

## 周回の 1 回

1. 走行中のクロールが在れば何もしません（全体で 1 本だけ走る決まりです）。
2. 「いま撮る」の頼みが在る予定を先に、次に期限の古い予定を 1 つ選びます。
3. 期限で始める予定は、**静かな時間**を見ます。API の起動と直近のクロールの両方から
   `CAPTURE_LEDGER_SCHEDULE_QUIET_MINUTES`（既定 10 分）が過ぎるまで始めません。「いま撮る」は見ません。
4. 宣言されたシークレットが Windmill に在るかを訊きます。
5. 1 つのトランザクションで、クロールの行と起点のページを足し、次の回へ進めます。
6. commit の後で webhook を投げます。

| 起きたこと                                                | どうなるか                                                                              |
| --------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| 走行中の行とぶつかった                                    | rollback します。期限は動かず、順番待ちのまま残ります。「見送り」という結末はありません |
| シークレットが足りない・Windmill に訊けない・行を足せない | `failed` の行を足し、次の回へ進みます                                                   |
| webhook を投げられなかった                                | 行を `failed` で閉じます（手で始めたクロールと同じです）                                |
| 台帳が止まっていた                                        | 戻ったときに 1 回だけ撮ります。過ぎた回の数は `crawls.schedule_missed` に残ります       |

走ったまま止まった行は、周回が勝手に閉じません。本当に走っている回を閉じないためです。状態が `stuck` になり、
画面の「締める」か `POST /api/crawls/:id/failed` で閉じます。

## 撮り方の固定

予定を作ったときに、`POST /api/crawls` と同じ確かめを通して解決した撮り方を `recipe` に残します。
スクリプトの本文の写しまで入るので、新しい版が出ても回の中身は変わりません。答えの `outdated` が
`true` になり、人が `repin` で固定し直します。シークレットだけは宣言を持ち、回ごとに Windmill へ訊き直します。

## 口

どの口も `maySubmit` で絞ります。一覧は 200 の空、それ以外は 404 で答えます。操作はすべて POST です
（capture-workbench の中継の書き込みは POST だけです）。

| 口                               | すること                                                                                                                                                                               |
| -------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /api/schedules`            | 本文は `{name, cron, request}`。`request` は `POST /api/crawls` と同じ形で、同じ理由で断ります。cron は 5 欄だけ受け、続く 20 回の間隔が下限より短ければ 400 です。同じ名前は 409 です |
| `GET /api/schedules`             | 消していない予定を、状態と直近の回つきで返します                                                                                                                                       |
| `GET /api/schedules/:id`         | 1 本。形は一覧の要素と同じです                                                                                                                                                         |
| `POST /api/schedules/:id/pause`  | 止めます。待っている「いま撮る」の頼みも消します。走っている回はそのままです                                                                                                           |
| `POST /api/schedules/:id/resume` | 再開します。次の期限は今から計算し直し、止めていた間は欠けに数えません。止めていない予定には何もしません                                                                               |
| `POST /api/schedules/:id/run`    | いま撮ります。202 を返し、周回が始めます。止めた予定でも撮れます                                                                                                                       |
| `POST /api/schedules/:id/repin`  | 頼みをいまの台帳で解決し直します。スクリプトが消えていれば同じ理由で断ります                                                                                                           |
| `POST /api/schedules/:id/delete` | 消します。行は残ります（クロールの行に名前を出すためです）                                                                                                                             |

`GET /api/crawls` と `GET /api/crawls/:id` は、`schedule`（`{id, name}` か `null`）・`scheduledFor`・
`scheduleMissed` も返します。

## 状態の語

`health` は上から順に見ます。文は capture-workbench が作り、台帳は語だけを返します。

| `health`  | 条件                                                              |
| --------- | ----------------------------------------------------------------- |
| `paused`  | 止めている                                                        |
| `stuck`   | 直近の回が 1 時間以上 `running` のまま                            |
| `overdue` | 期限または「いま撮る」の頼みから 1 時間以上たっても始まっていない |
| `failing` | 直近の回の `state` が `failed`                                    |
| `blocked` | 期限は来たが、走行中か静かな時間の待ち                            |
| `ok`      | 上のどれでもない                                                  |

`stuck` を分けているのは、毎日の予定は次の期限が約 24 時間先だからです。期限だけで見ると、04:00 に止まった回が
翌朝の 05:00 まで何も言いません。

## 設定

| 環境変数                                       | 既定 | 効果                                                                            |
| ---------------------------------------------- | ---- | ------------------------------------------------------------------------------- |
| `CAPTURE_LEDGER_SCHEDULE_QUIET_MINUTES`        | `10` | 静かな時間。`dev:up` がトークンを発行し直す前と、e2e の間に割り込まないためです |
| `CAPTURE_LEDGER_SCHEDULE_MIN_INTERVAL_MINUTES` | `60` | 周期の下限                                                                      |

クロールの口（webhook の 2 行）が無い配備では、口も周回もありません。
