import { browserhivePin } from "../../../lib/extract";

capture-ledger は `main` ではなく **特定の BrowserHive の版**に固定されています。
現在のピンは **{browserhivePin()}** です。

これは `.upstream/browserhive` submodule から来ています。ビルド時に `git describe --tags`
で読んでいるので、このページが古くなることはありません。この submodule には、BrowserHive
本体・BrowserHive が検証済みの
`chromium-server-docker`・署名のサービス（`wacz-signer`・`timestamp-authority`）・manifest を照らす
OpenAPI 文書（`generated/openapi.json`）が入っています。**ピンはこれだけではありません。** object
store の起動設定は `.upstream/seaweedfs`、WACZ のビューアは `.upstream/replayweb-server`（改変していない ReplayWeb.page）と
`.upstream/capture-player`（改変した Web Capture のビューア）、
取り込み対象のフィクスチャは `.upstream/capture-fixtures`、スクリプトは `.upstream/capture-scripts`
から来ます。それぞれが自分のタグに固定されていて、この submodule を上げても動きません（スタックが
build に使う物を分けてある理由は、`docker-compose.yml` の冒頭にあります）。

:::note[以前は 4 箇所ありました]
かつては `package.json`・setup.sh（いまは無い）・compose 2 枚にバージョン文字列が書かれ、
それらが食い違わないか検査していました。submodule が 4 つとも置き換えたので、
**同期を保つべき対象がもう存在しません**。
:::

## 手順

```sh
# 1. submodule を新しいタグへ動かす。
git -C .upstream/browserhive fetch --tags
git -C .upstream/browserhive checkout <new-tag>
git -C .upstream/browserhive submodule update --init --recursive
git add .upstream/browserhive

# 2. 契約を取り直して型を再生成する（ローカルコピー。ネットワーク不要）。
pnpm run openapi:generate
pnpm run openapi:check     # コミット後に exit 0 になること

# 3. 新しい submodule で dev のスタックを建て直す。fixtures はサービス名を付ける。
#    無いと stack:up はスタックの全部のコンテナを作り直す。
pnpm run dev:down
pnpm run dev:up
pnpm run stack:up --profile capture-fixtures capture-fixtures

# 4. 端から端まで確認する。
pnpm run check
(cd ../capture-scheduler && pnpm run smoke)
```

Chromium は自動的に追随します。submodule の submodule なので、
**BrowserHive 自身が検証した版**がそのまま手に入ります。以前 capture-ledger は
これを独立に `main` で追跡しており、それがスタック崩壊の原因になりました —
上流が開発用 Dockerfile を `attic/` へ移した瞬間、すべてのビルドが止まりました。

## 版の選び方

:::danger[その版がビルドできるか先に確認する]
スタックは submodule から BrowserHive の `Dockerfile.prod` をビルドするので、
Dockerfile が壊れているコミットを掴むとスタックごと立ちません。実際に一度
起きています。**2 度とも同じファイル**です: `8a66b72` から `b772480` の間は
BrowserHive の whitelist dockerignore に COPY 対象が 1 つ足りず、BrowserHive の
`8c899dd` から `a218e94` の間は、消したはずの `tsconfig.behaviors.json` を COPY が
名指ししたままでした。どちらの区間も
`"/tsconfig.behaviors.json": not found` で失敗します。**v11.0.0 はビルドできます**が、
2 つ目の区間を指したまま固定すると立ちません。

submodule の更新をコミットする前に確かめてください。

```sh
# -f は context ではなく今いる場所からの相対で解決されるので、context を含む
# パスで書くこと。`-f Dockerfile.prod` だと "dockerfile does not exist" になる。
container build -f .upstream/browserhive/Dockerfile.prod -t bh-probe .upstream/browserhive
```

:::

## capture-ledger 側で何が変わるか

API の追加だけの変更 (オプショナルなリクエストフィールドが増える等) なら、手順 2
以外は何も要りません。再生成した型はそのままコンパイルが通り、テストも無修正で
通ります。1.6.0 はまさにこれでした。upstream は変更のたびに前のリリースとの
`smithy diff` を回しているので、項目が増えただけの更新で既存の項目の名前や型が
写しの下から変わることはありません。

厄介なのは**インフラの変更**です。OpenAPI の差分にはまったく現れません。
1.5.2 → 1.6.0 の移行で実際にあった 2 例:

- BrowserHive の SeaweedFS entrypoint がバケットを自分で作るようになり、capture-ledger
  側の一発 init コンテナが不要になった (同時に `depends_on` による順序保証も
  意味を失い、`WAIT_FOR_S3` が置き換えた)。
- 上流の Chromium イメージが開発用 Dockerfile を `attic/` へ退避させた。

ピンを上げたら、`etc/seaweedfs/*`・entrypoint・compose の契約に触れる変更が
無いか、上流のリリースノートを読んでください。

### manifest の照合が通すもの

段の登録・reconcile・1 ページのログのエンドポイント・取り込みの経緯のエンドポイント・失敗の時点の絵のエンドポイントは、どれも `.result.json` を `readManifest`
（`src/archive/manifest.ts`）で読み、写した `CaptureResultReport` に Ajv で照らします。版を上げると、
ここで次のことが効きます。

- **写しが知らない項目は通します。** 新しい BrowserHive の manifest も読めるので、写しを上げる前に
  BrowserHive の版が上がっても、capture-ledger は止まりません。写しが知らない enum の値は通しません。
  写しを上げるまで、段の登録と reconcile はその manifest を飛ばし、1 ページのログのエンドポイントと
  取り込みの経緯のエンドポイントは `manifest-invalid` と答え、失敗の時点の絵のエンドポイントは 404 と答えます。
- **契約が既定値を持つ項目は、欠けていれば補います**（`useDefaults`）。後から `@default`
  つきで必須になった項目は、古い manifest を落としません。既定値の無い必須の項目が増えたときと、enum
  の値が消えたときは落とします —— 上げる前に、新旧の `openapi.json` どうしで `required` と `enum`
  を比べてください。
- **任意の項目は、無いまま残ります。** v24.0.0 の `log` は既定値を持たないので、それより前の
  manifest は、空の log ではなく `log` の無い物として読まれます。1 ページのログのエンドポイントが、
  空のログを見せずに `no-log` と言えるのはこのためです。
- **契約に `format` が入ると、API が起動しません。** Ajv は `date-time` も `double`
  も知らず（ajv-formats は入れていません）、`src/archive/manifest.ts` を import した時点で compile
  が投げます。manifest を読む試験も全部落ちます。compile するのは `CaptureResultReport` から辿れる
  schema だけなので、上げる前にそこに `format` が増えていないかを見てください。
